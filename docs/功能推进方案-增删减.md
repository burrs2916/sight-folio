> 口径：**「一致性」= 本产品唯一差异化论点**（伏笔、人物出场、时间线、剧情线、世界观、风格）。

## 〇、一句话诊断

产品的**编辑层是干净的自有域**，但**「全书级洞察」整层寄生在已封存的代码分析设施上**，而真正能对外传播的那套体检引擎**已经写好，却只喂给了 AI、没有给用户看**。

所以功能层的正确动作不是"加新功能"，而是：**接断线 → 把已有引擎变成可见产品 → 给 AI 长出手脚 → 砍掉 2.8 万行死重**。

## 三、增（按性价比排序，全部服务一致性论点）

### 增-1 ★★★★★ 把已有的「全书体检报告」从 AI 语料升格为用户可见的一页报告

> **⚠ 本条已于 2026-10-28 实施时修正（原判断部分错误，保留以免后人误读）**
>
> 原文断言"体检结果唯一消费者是 AI prompt、作者看不到"——**错**。核查后实情是：
> `buildProofreadReport` 有 **4 个消费者**，其中 3 个是界面：校对页签编辑面
> （`writingPanes.tsx:1789`）、画布右栏要素卡 `ProofreadOverviewCard`、全书总览
> （`writingOverview.ts:151`）。只有 `buildProofreadCorpus`（语料格式化层）是 AI 专用。
>
> 真正的缺口是另外两个，且比"不可见"更隐蔽：
> ① **全书体检只在场景画布里**，写作台不可达；而写作台工具栏那个「校对」按钮打开的是
>    **当前章**错字面板（`ProofreadPanel`），同名不同物，作者会以为全书体检就是它。
> ② **规则覆盖缺**：跨章人物账本（零提及 / 重名卡 / 别名未登记 / 长期失踪）完全没有，
>    而"死设定"此前只能通过 `scan_writing_book` 写进代码域 `review_findings` 才检得出——
>    作者不点「解析全书」就永远看不到。
>
> 已按此实施，见本节末「实施记录」。

**这是本次分析最大的单点发现。** `utils/writingCorpus.ts:buildProofreadCorpus` 已经在算并且算得很全：空章、标记完稿但 0 字、伏笔回收点已过仍未回收、时间线冲突事件、时间线待补全草稿、剧情线未挂线事件、念头池未分发念头（`writingCorpus.ts:421,465-480`）。时间线冲突检测（`273-289`，两视图并集口径）与人物/世界观自洽核对（`672-679`）也都已存在。

**但它的唯一消费者是 AI prompt**（注释原话："供校对题材的 AI 消息自动注入"）。作者看不到。

要做的是：同一份 `buildProofreadReport` 输出一个「体检」面板/一页可导出报告 + 逐条可跳转到具体章节。**几乎零新算法，纯可见性改造。** 这一件做完，产品就有了能一句话说清、当场演示、别家没有的东西。

#### 实施记录（2026-10-28，批次② 第一部分）

**刻意没有新建第二份引擎**——本仓库在 `ProofreadPanels.tsx` 顶部就写着「口径 =
`utils/writingProofread.buildProofreadReport`，禁止第二份」。所以全部改动都是**扩展原引擎**：

1. 引擎从六组扩到**七组**，新增 `consistency` 组（`writingProofread.ts`）：
   - `normalizeSettingName` / `settingMentionTerms`（卡名 ∪ `extra.aliases`，**零迁移**）
     / `computeSettingAppearances`（逐章提及账本 + 最长断档）
   - 四条规则：归一化重名卡（`block`）、正文零提及的死设定（`warning`）、
     疑似别名未登记（与前一条**互斥**，不重复报同一张卡）、出场中断档 ≥30 章且全书 ≥40 章
   - 刻意**不做编辑距离模糊匹配**：中文名「李明 / 李强」距离同样是 1，但那是两个人。
     阈值取小天天报警、取大检不出，所以只用确定性的归一化全等与前缀两条。
   - 关键性质：**只看写作域自有数据**，不读扫描层 `metadata.appearances` ——
     体检不该因为"忘了点一个按钮"而漏报。
2. 补上此前 `void storylines` 占位的**空剧情线**检测（一条报线名、多条报计数）。
3. `ProofreadTarget` 新增 `{ type: 'setting'; id }`：一致性发现**直接打开那张出问题的卡**，
   而不是泛泛跳「人物页签」。画布侧 `jumpIssue` 与写作台侧各自落地。
4. 四处调用点全部传入 `settings`，新发现在校对页签、画布要素卡、全书总览、AI 体检语料
   四条链路上**同时生效**（不是只加一个新界面）。
5. 新增 `WritingHealthDialog`（写作台内七组清单 + 严重度过滤 + 排序 + 逐条跳转）。
   入口挂在**右抽屉提醒区之上**，不新增工具栏图标（遵循批次④的减入口原则）；
   且**0 项也显示**——「全书没查出问题」本身就是作者要看到的信息。
6. 发现数角标刻意用 1.5s 去抖而非 `useMemo`：整本报告要扫全书正文，成本与总字数成正比，
   挂在渲染路径上会直接拖慢输入。

验证：`tsc` 0 error；`eslint` 核心文件 0 告警；`vitest` **151 文件 / 1843 用例全绿**
（新增 15 条规则单测，重点锁**误报**反向边界：单字名不参评、整本未写不算死设定、
短书不报断档、疑似别名不重复报、不传 settings 时整组静默）；i18n zh/en 各 5,894 键零差集。

#### 出场图谱改数据源（同日第二部分，批次② 收尾）

把 `WritingAppearanceMatrix` 从扫描产物切到写作域派生，**「必须先解析全书」这个门槛从根上消失**。

- 改造前：章节 = `project_files` 里 `writing://` 虚拟行；出场次数 = `metadata.appearances`；
  死设定 = `findings` 里 `ruleId=writing-dead-setting`。三样全是扫描产物，没解析就是白图。
- 改造后：章节 = `writingStore.chapters`；出场与死设定 = 体检引擎同一份
  `computeSettingAppearances`（为此给它补了 `countsByChapter` 逐章计数）。
- **顺带消除了一个隐患**：图谱与体检现在共用同一份计数。此前两者若各算一套，
  同一个作者会在两处看到互相矛盾的出场数字。
- 与 `writingOutline.chaptersOfSetting`（作者显式挂到节拍 = 计划）是**两个不同事实**，
  本就该不一致，不一致本身正是要看的东西——已在文件头写清，防止后人当重复实现合并掉。
- 批次① 给空态加的 `onScan`「立即解析全书」按钮**已随之撤除**：那是为绕开这个坑贴的创可贴，
  坑填了就不该留着。空态改为区分「没章节」与「没建卡」两种（原文案会把人指错方向）。

**过程中修掉的真 bug**：表头按热度降序排序，单元格却遍历未排序的原数组取数 —— **列会错位**，
名字和数字对不上。新测试用 DOM 顺序做位置断言锁住它（按 id 反查永远对得上，抓不到这类错位）。

**遗留**：后端 `scan_writing_book` 仍在产出 `writing-dead-setting` finding，但**前端已无消费者**
（唯一残留是解释性注释）。它现在是纯冗余产出，列入批次④ 的死代码删除清单。

#### 一页体检报告导出（同日第三部分）

新增 `utils/writingHealthReport.ts`（纯函数）+ 体检面板底部两个导出按钮（Markdown / 自包含 HTML）。

- **刻意只做这两种纯文本自包含格式**，不接既有 PDF/DOCX/EPUB 那条导出链——那条链自身的排版
  缺陷（EPUB 无 CSS、DOCX 缺 `styles.xml`、PDF 表格残渣）本文已记为待办，报告不该被拖累。
  HTML 版自带 `@media print` 样式，浏览器打开即可「打印成 PDF」，零新依赖。
- **口径不重算**：入参 `report` 由面板从 `buildProofreadReport` 传入，保证
  「屏幕上看到什么就导出什么」，不会出现两套结论。
- **MD 与 HTML 共用同一套拆行逻辑**（`issueParts`）：两个序列化器各定一套规则的话，
  同一份报告在两种导出里会长得不一样。
- **转义是硬要求不是洁癖**：章名、设定名、伏笔标题全是作者自由文本，
  不转义等于允许正文里一段 `<script>` 跟着报告一起被导出去。已有测试直接锁这一点。
- 落盘沿用既有六格式导出的同一套约定：`plugin-dialog` 选路径 → `save_text_file` 写入，
  **用户取消静默返回（不算失败）**，真失败给 error toast。

**测试过程中纠正的两处认知**（都不是 bug，是引擎口径，已写成断言固定下来）：
① 章账判定是「空章」优先于「谎报完稿」（else-if），后者要求**有正文但字数记 0**；
② 整本无正文时一致性组必须整组静默——否则新书一打开就满屏「人物集体缺席」。

### 增-2 ★★★★★ 给 AI 加语料库工具 ✅已完成（2026-10-28）

**实施记录（批次③ 第一项）**：后端新增只读工具 `search_corpus`（`CorpusSearchTool`），
复用 `SqliteCorpusRepository::search_with_total`，前端四处同步接通启用链路。

关键实现决定：

- **输出预算比通用 `code_search` 保守一个量级**（默认 8 条 / 硬上限 20 条 / 单句 300 字）。
  语料命中本身就是**要喂进上下文的正文**，条数一多等于把语料库整段搬进对话，
  一次调用就能烧光预算。`tools.rs` 文件头部明确要求每个工具自我设界，本工具照做，
  且截断时**明说**并给出继续的确切参数。
- **按字符而非字节截断**：中文一字三字节，按字节切会落在字符中间直接 panic。
- **查不到时明说「库里没有」并写明「不要编造参考句」**。语料工具最大的风险不是查不到，
  而是模型查不到就自己造一句冒充参考。
- **语料库不可用时不注册该工具**（`corpus_repo: None` → 直接跳过注册），
  而不是注册一个每次调用都报错的工具。
- 输出**必带出处**（书名 + 章标题 + 参考价值分层 + 出现次数），否则模型无法向作者交代来源。

启用链路（漏掉任何一处，工具注册了也永远不会被调用）：`WRITING_TOOLS` 默认白名单、
`availableTools` 目录、写作助手系统提示词（中英各加一条"谈文风必须先查语料库、
查不到要直说"）、`agent.form.tools` 双语键。

测试 5 条：真实命中带出处、空 query 必须报失败、查不到不许编、
limit 被夹到硬上限、**注册与降级两条链路本身**（用 `registry.get()` 断言）。

**顺带修掉一个被本次改动暴露的既有缺陷**：`CorpusState::try_begin_maintenance` 是 `pub fn`
却返回模块私有的 `struct MaintenanceGuard`，触发 `private_interfaces`。此前 `CorpusState`
没被跨模块引用所以没暴露；本次 `commands/agent` 引入它之后 lint 计数 179→180。
已把守卫可见性放宽为 `pub(crate)`（仅可见性，`Drop` 语义与用途不变），lint 回到基线 179。

#### 原始分析（实施前判断，保留备查）

`plugins/ai_agent/tools.rs` 注册 16 个工具（`apply_change`/`code_search`/`write_chapter`/`read_character_card`…），**没有任何 corpus 工具**（`ai_agent/*.rs` 全文 grep `corpus` 为空）。263 MB 语料库对 Agent 而言"只能被 UI 读，不能被 Agent 查"。
补一个 `search_corpus` 只读工具（复用现成 `corpus_repository` 查询）成本约一天，直接解锁"AI 引用你自己沉淀的语料写作"。这是当前最便宜、最能拉开与通用 AI 差距的一项。

### 增-3 ★★★★ AI 缺「改设定」的手 ✅已完成（2026-10-28，批次③ 第二项）

新增写工具 `update_character_card`，与 `write_chapter` **同规格**落地：

| 安全设计 | 做法 |
| --- | --- |
| **审批** | 登记进 `approval_mode` 的 `SessionOnce` 组，并写 `approval_summary`（说清动哪张卡、动哪几个字段、AI 给的理由） |
| **防整行覆写** | `save_setting` 是整行 upsert。工具**先读现有卡、只覆盖模型显式传入的字段**，其余原样保留 |
| **改前存历史** | 新增 `writing_setting_revisions` 表，改写前先把**旧值**存进去（每卡滚动保留 20 次） |
| **扩展字段保护** | `extra` 解析失败或不是对象时**拒绝改别名**，绝不拿空对象盖掉作者的关系网 |
| **自我设界** | 描述 4000 字上限、别名 40 个上限、单字别名拒收（与体检提及口径一致，否则制造永远检不出的假别名） |

两处值得记的判断：

1. **为什么补一张历史表**：本仓库对 AI 写正文的规矩是「覆盖前必存快照」（`write_chapter`
   里写着"数据安全铁律"）。设定卡同样是书稿，而且是**改错就还原不回来**的结构化内容。
   只加写工具不加历史，等于给了 AI 一把没有保险栓的枪。

**四个值得记的决定**

1. **存储用全局 KV（`settingsApi` → `SqliteSettingsRepository`），刻意不用 localStorage**。
   词库是**作者的资产**，必须跟着库文件走——能被备份、能换机带走。散在浏览器存储里的
   作者配置等于没有。（与批次② 刚删掉的「快照写 localStorage」是同一条判断。）
2. **`ignored` 白名单不是附加功能，是词库能扩张的前提**。项目一条贯穿约束是
   **误报比漏报更严重**：漏一个错别字作者自己会看见，而词表误伤人名/术语（角色名叫「在在」
   就会命中内置 `在在→在/再`），报多了作者会直接把整个校对面板关掉。没有关掉的口子，
   词库越"聪明"越没人用。
3. **敏感词合并后必须按词长降序重排**。内置那份 `SENSITIVE_WORDS_SORTED` 是
   `sort((a,b) => b.word.length - a.word.length)`（长词优先，避免短词抢先命中同一区间）。
   只在内置上排序、把自定义**追加在尾部**，自定义短词就会插队——这条最容易在
   "看起来能用"的状态下埋进去，故单独立测试钉住。
4. **畸形条目一律丢弃，绝不进引擎**。`text.indexOf(undefined)` 不是报错，而是去匹配
   字符串 `"undefined"`——会凭空造出一堆误报。`normalizeLexicon` 把空词形、缺字段条目
   全部丢掉，并保证每个分支都**新建数组**（`EMPTY_LEXICON` 是导出常量，交出去被 push
   一次就污染全局"空词库"）。

另外两点：同名词形**作者覆盖内置**（否则内置表成了不可协商的权威，作者只能整条 ignore，
连带丢掉这条本来有用的提醒）；管理界面**每次增删立即落库 + 失败回滚界面**，不用

### 增-7 ★★★ 认知权重的 0 值语义 ✅已完成（2026-10-28，批次③ 第三项）
**订正原判断**：原文写"要么禁止 0，要么把 0 定义为**最低权重**"。后半句是错的——六维都是
双极轴（集体↔个人、理性↔感性、宿命↔自由…），`-10..+10` 的 **0 是中点「中立」，不是最低**。
最低强度是 `±1`；0 表达的是"这一维他确实不偏不倚"，是长篇人设里有信息量、作者会主动用的设定。

**实测确认是三处叠加丢语义**（原先只写了一处）：

| 位置 | 旧代码 | 后果 |
| --- | --- | --- |
| 卡面板滑块 | `(v as number) === 0 ? null : v` | 拖到中间＝请求"清除" |
| 写入 `setCognitiveWeightField` | `value !== null && value !== 0` 才存，否则 `delete` | 0 落不了库 |
| AI 上下文 `fmtWeight` | `n !== undefined && n !== 0` 才输出 | 即使库里有 0，prompt 也不体现 |

于是滑块停在 0、作者以为记上了，库里什么都没有，AI 也当作这一维从未被设定。

**做法**：新增 `utils/writingCognitiveWeights.ts` 作为**单一口径**，明确
`null = 未设置（删该维，AI 不猜）` / `0 = 中立（落库并告知 AI）`，并顺手收掉两处更深的漂移：

1. **六维清单原本有两份字面量**：卡面板走 i18n 取词，而 AI 侧 `fmtWeight` 把
   `'集体'/'个人'/'信任'/'怀疑'…` **硬编码成中文**，连行首 `——决策倾向：` 也是硬编码中文。
   现在维度清单（`COGNITIVE_DIMENSIONS`：key + i18n 键）与格式化都在 utils 一处，
   展示词与标题由调用方注入已翻译文本，工具函数本身不碰 i18n。
2. **「均衡」不引入新术语**：用该维两端的既有词拼。语序交给模板键 `writing.cwBalancedPattern`——
   中文「理性/感性均衡」，英文要 `"Rational/Emotional balanced"`，硬拼会写成
   `Rational/Emotionalbalanced`。
3. **UI 三态可见**：`未设置` / `中立` / `偏向端+幅度` 的文字与颜色各不相同，并补
   `cognitiveWeightsHint` 说明「中立会写进 AI 上下文，未设置则 AI 不替他猜」；
   回到"未设置"改用右侧清除按钮，**不再靠把滑块拖到 0**（那正是混淆源头）。
4. 越界值统一 `clampCognitiveWeight` 夹到 ±10、非有限值按 0（防手改 JSON 造出 ±100 的畸形卡）。

**测试**（12 条 `writingCognitiveWeights.test.ts`）锁语义而非渲染：0 必须落库、null 才删、
删到空返回 `undefined` 让上层清键、不改传入对象（extra 是共享引用）、0 会出现在喂 AI 的那一行、
全未设置时返回 `null`（不印空标题）。另两条防回归：六维 i18n 键必须真实存在；
**剥掉注释后 utils 源码里不得再出现「集体/理性/信任…」等中文常量**——直接挡住"顺手把词写回代码"。

### 五批：死函数与常量（约 90 行）+ 一条必须记住的 lint 陷阱

删：`engine.rs` 的 `list_names`/`filter_keep`、`parser::supports_ast`、
`corpus_repository::read_chunk`、`CorpusChunk` struct、`insight_status::PARTIAL`、
`extract_c_like_symbols_with_fallback`。

> **`dead_code` lint 不能单独作为删除判据。**
>
> `cargo check --all-targets` 依然会把「只被 `#[cfg(test)]` 使用」的函数报成
> `never used`——因为 `dead_code` 按编译单元计算，**lib 单元看不见 test 代码**。
> 我照 29 条 lint 批量删了 11 项，编译器立刻回吐 17 个 error：
> `open_in_memory`（39 处调用）、`parse_anthropic_response`、`CodeSearchTool::new`
> 全是测试在用的。全部回滚重做。
>
> 讽刺的是我在动手前刚写下"必须防 `cargo check` 不覆盖测试导致的假阳性"，
> 然后用了一个**自以为**覆盖了测试的口径（`--all-targets`）并相信了它。
> `--all-targets` 只是多编译一个 test target，lib target 的 lint 结论不变。
>
> 可用的判据只有一条：**按定义之外的引用位置分类**——
> A 零引用（可删）／B 只被 test 引用（删要连带改测试）／C 被 lib 引用（lint 假阳性，禁删）。
> 29 条 lint 里真正落在 A 的只有 8 条。
>
> 两个附带的判据陷阱：
> - 对 `new` / `chat` / `search` / `message` / `is_empty` 这类通用名，
>   grep 同名符号计数毫无意义（`is_empty` 全仓 779 次）。
> - **trait 方法不能凭"0 引用"判死**：各 `impl` 里的 `fn foo(...)` 会被当成定义跳过，
>   于是 `validate_config`、`unbind_notes_from_chapter` 都显示 0 引用，实际有实现。

**标记待决的一条断线**：`extract_c_like_symbols_ast` 及其专用
`c_record_kind`/`c_decl_name`/`c_signature`/`c_modifiers`（约 250 行）。
注释写着「C/C++ 走 AST 版」，但真正的调用方 `parser/c_like.rs`、`parser/other.rs`
用的是逐行正则版 `extract_c_like_symbols`，而该函数自己的注释承认它
"实测 libredwg/src 291 个文件只抽出 34 个符号，全是 struct/typedef"。
也就是说 **AST 版是写好却从未接线的实现**，线上跑的是弱版本。
它属代码分析域，去留跟着 `/analyzer` 的决策走；风险不对称（留着只多 250 行和一条
warning），故本轮不动。若将来决定保留 `/analyzer` 并要提升 C/C++ 分析质量，
这是一条已经写完、只差接线的现成路径。
