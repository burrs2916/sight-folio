## 3. 🟡 新发现 A（P2）：界面语言还有**第二条没登记的落盘通道** —— `i18n/index.ts` 自己写 localStorage

**取证（实测引用点）**：

```
src/i18n/index.ts:32  const STORAGE_KEY = "project-sight-locale";
src/i18n/index.ts:43  getInitialLang() → localStorage.getItem(STORAGE_KEY)      // 读
src/i18n/index.ts:59-64  persist(lang) → localStorage.setItem(STORAGE_KEY, lang) // 写
src/i18n/index.ts:73  applyLang() 里调用 persist()
src/store/languageStore.ts:22  LEGACY_LANGUAGE_STORAGE_KEY = 'project-sight-locale'
src/store/languageStore.ts:85  localStorage.removeItem(LEGACY_LANGUAGE_STORAGE_KEY)  // 只在这一条分支里
```

**为什么会发生**：第 19 轮的口径是「语言迁进设置库、旧 localStorage 值**一次性迁移并清理**」，
但 `languageStore` 每次生效都要调 `i18n.setLang()`（`setLanguage` / `hydrate` / `init` 三条路都调），
而 `setLang → applyLang → persist()` 会**把旧键重新写回去**。
只有「设置库为空 + 走旧值迁移」那一条分支会在写完后再 `removeItem` 清掉；正常读回分支不清。

**实测后果（逐条，不夸大）**：

1. 台账里「旧值一次性迁移并清理」这句在稳态下**不成立** —— 用户每换一次语言，旧键就回来一次。
2. `languagePersistence.test.ts:68` 那条 `toBeNull()` 断言只在迁移分支上成立，所以它**测不到这条漏**。
3. 现在**不是**用户可见缺陷：`languageStore.init()` 优先采信设置库读数，会把 i18n 的初值盖掉。
   唯一能吃进脏值的路径是 `init()` 的 `catch` 分支（`:96 set({ lang: getLang() })`）——
   它读的是本次启动时 i18n 从**旧 localStorage** 推出来的值。设置库读失败 + 旧键是陈旧值 ⇒ 语言回退。
4. 真正的代价是**下一轮的判断成本**：谁再读推进记录，会以为语言只有一个真源，于是把「加一格语言相关设置」
   接到 `i18n` 那一侧，那就又是一处「改了没生效」。同族病灶本仓已经清过三轮（第 19 / 25 / 30 轮）。

**建议修法（一刀，约 10 行 + 一把扫描锁）**：
`i18n/index.ts` 的 `persist()` 删掉 `localStorage.setItem`，只保留 `document.documentElement.lang` 属性与订阅通知；
`getInitialLang()` 删掉旧键读取（首帧兜底改走 `navigator.language`）—— 旧值的**读与清迁仍归 `languageStore` 独管**。
⚠ 同批改 `init()` 的 `catch` 兜底：不许再拿「i18n 从旧键推出来的值」当兜底，应保留内存现值（与第 34 轮
「迟到读数不许盖用户改动」是同一条尺）。最后补一把扫描锁：`project-sight-locale` 作为**代码**只许出现在
`languageStore` 的 `loadLegacyLang` / `removeItem` 两处（照第 36 轮 `settingsRound36.test.ts:138` 那条
「旧 localStorage 键名只许出现在迁移函数里」的写法抄，判据先剥注释 —— 第 35 轮自纠记过这条坑）。
