## 1. 块一 · system 层拆分契约

### 1.1 拆分原则

- **进 system**：跨任务、跨轮次稳定的**行为契约**（怎么工作、何时认怂、输出纪律、回复语言）。
- **留在 user**：**本轮事实**（上下文/语料/选区/诊断）与本轮请求。模式指令介于两者之间（见 1.4 单独拍板）。
- **不动**：快捷动作/追问（`workbenchPanelHooks.ts`）是 UI 建议词条，不是发给模型的提示词，不参与拆分。

### 1.2 逐段去向建议表

| 段 | 现状位置 | 建议去向 | 动 Rust？ |
|---|---|---|---|
| 用户人设 | system 槽位（用户可改） | **保留唯一可编辑位**，文案升级为 §1.5 草案 v2（可选项） | 否 |
| 应用契约块（新） | 无 | **代码拼装，追加在 system 槽位之后**：盲区声明 + 结构化输出纪律 + 语言指令（§1.3 全文） | **是**（run_agent 增可选 `extra_system`，见 1.4 方案 S） |
| 模式/题材角色指令 | user 头部，每轮重复 | 方案 S 落地后随契约块进 system；**未落地则维持现状**（气泡观感已由 `extractUserMessageView` 兜住） | 随 S |
| 上下文/概览/作用域/诊断块 | user 尾部 | 留 user（本轮事实，进 system 反而稀释注意力、破坏多轮一致性） | 否 |
| 画布 ops 人设+schema+硬规则 | user（独立一次性任务） | 留 user（自带完整契约，与工作室人设不同生命周期）；仅语言行改指真源（块三） | 否 |
| 续写/润色/改写/总结/审校/补全任务指令 | user | 留 user（任务级契约，逐字是「本轮要什么」）；仅语言行收真源（块三） | 否 |
| 审校 preset / 语料 provider 说明文案 | user（语料包内嵌） | 留 user（随语料走） | 否 |

### 1.3 「应用契约块」草案全文（代码拼装、用户不可编辑、追加在人设之后）

中文（UI 语言=zh 时）：

```text
【应用契约 · 必须遵守】
1. 材料即边界：涉及本书设定、正文、时间线、伏笔、统计的结论，只能依据本轮消息注入的上下文
   或你亲手调用工具（file_read / project_context / scan_records 等）读到的真实内容；
   材料覆盖不到的，明确说「现有材料无法支持这一判断」，绝不编造情节、设定、数据或引用。
2. 产出形态：被要求修改正文/文件时优先用工具落实，不要只给建议不动手（当前模式禁止写盘除外）；
   被要求输出结构化结果（JSON / 一行式条目 / 表格）时只输出结果本体，无解释、无前后缀、无代码围栏。
3. 作者意图优先：润色与改写默认保留原作语感，给建议先说理由；未被明确要求时不评价文风、不催更、
   不替作者做剧情走向决定。
4. 回复语言以下方语言指令为准。
```

English（UI 语言=en 时）：

```text
[Application contract — mandatory]
1. Material is the boundary: conclusions about this book's settings, prose, timeline,
   foreshadowing, or stats may only rest on the context injected into this message or on
   facts you read via tools (file_read / project_context / scan_records). Where material
   cannot support a judgment, say so explicitly; never fabricate plot, settings, data, or quotes.
2. Output discipline: when asked to change prose or files, act with the provided tools rather
   than only advising (unless the current mode forbids writing); when asked for structured
   output (JSON / one-line entries / tables), output only the result — no explanations,
   no prefixes, no code fences.
3. Author intent first: polishing and rewriting default to preserving the original voice;
   give reasons before suggestions; never judge style, nag for updates, or decide plot
   directions unless explicitly asked.
4. Reply in the language stated by the language directive below.
```

语言指令（并入契约块末行，双语口径沿用现 i18n 键 `ai.respondZh`/`ai.respondEn`）：
`请使用简体中文回复所有结论、标题与说明。` / 现 en 包 `respondEn` 原文。

### 1.4 配置口三选一（**拍板点 P-1**）

| 方案 | 内容 | 代价 | 风险 |
|---|---|---|---|
| **S（推荐）** | 契约块由代码拼进 system（Rust `run_agent` 增可选 `extra_system: Option<String>`，engine 拼在人设后；照批次 2 先例带 `cargo test --lib` 锁）；**不新增设置域**，人设仍是唯一可编辑位 | 前端 1 处拼装 + Rust 签名/调用点/1 锁测 | 契约文本改了体感全变 ⇒ 上线即钉版，改动走 MR 式评审 |
| T（零 Rust） | 契约块仍拼在 user 消息头部（与模式指令同段） | 最小 | 违背 system/user 分层初衷；每轮重复 ~200 token；「指令随消息走」在多轮里被历史稀释 |
| C（全配置化） | 契约块做成设置域（开关 + 可编辑文本） | 7 件套一次交齐（落库 scope/init 读回/跨窗口 hydrate/抽屉入口/真实消费点/备份键/恢复默认），第 30 轮反面样本警告 | 用户改坏契约 = 体感事故自己背；对写作软件是过度暴露 |

## 2. 块二 · few-shot 示例

**现状**（grep 复核）：全仓 few-shot 仅 1 例 = `writingAssistant.ts:377-388` 逐句审校的「第1句|他是我的一个朋友。|成分赘余|他是我朋友。」示范行。该例质量高（输入形态+分隔符+枚举白名单+空结果兜底俱全），可作其余示例的**口径模板**。

### 2.1 建议新增 1 · 画布 ops（**拍板点 P-2.1**，收益最大）

画布有 schema + 7 条硬规则，但模型从未见过一个合法输出长什么样；「只输出 JSON 数组、无围栏」是失败率最高的那条约束。在【硬性规则】之后、实体清单之前插一行示例（中文分支；EN 同构）：

```text
【示例】指令「把选中的三张卡片排成一行」→ [{"op":"arrange_grid","ids":["n-3","n-7","n-9"],"columns":3}]
```

- 成本：+~40 字符/次（≈25 token）。风险：示例可能诱导模型只回单 op——示例特意用 `arrange_grid` 多 id 形态规避。

### 2.2 建议新增 2 · 设定卡补全（**拍板点 P-2.2**）

现契约（`:498-501`）说了「只输出 JSON 对象」但没给形状。在契约句后追加一行：

```text
示例（需补全 appearance、motivation 时）：
{"appearance":"…","motivation":"…"}
```

- 成本：+~50 字符/次。解析端 `parseSettingCompletion` 本就宽容，示例只降「前言+围栏」返工率。

### 2.3 明确**不建议**做的（写出来供确认「不做」）

- **工作室 edit 模式的补丁格式 few-shot**：edit 主路径是 `apply_change` 工具，给文本块补丁加示例会诱导模型「演」补丁而不调工具，与现有「优先用工具」指令打架。
- **续写/润色的 few-shot**：小说文本示例会被当成风格锚，污染作者文风指纹；生成类任务的质量锚已经是风格指纹注入机制（`styleRequirementBlock`），不叠第二套。

## 4. 块四 · 温度 0.7 / 迭代 10 是否分档

**机制复核**（本轮实测，修正任务书表述）：温度/迭代**不是写死的 0.7/10**，而是助手表单值（`AiAgentPage.tsx:2683-2684` 仅缺省）；用户建的每个助手各有一份，工作室与写作内联任务共用**同一个助手记录**才导致「全任务共用」。迭代 10 在 `engine.rs:653-656` 证实只是工具循环上限——无工具调用一轮即 break，续写/审校这类一次性任务**不因它多花一分钱**。⇒ **真正要分档的只有 temperature；迭代分档可不做。**

**任务性质分档建议**（若做）：

| 档 | 任务 | 建议温度 | 理由 |
|---|---|---|---|
| 生成 | 续写 / 润色 / 改写 / 画布文案 / 设定补全 / 构思脑暴 | **0.7（现值不动）** | 创意多样性正当 |
| 判别 | 逐句审校 / 逻辑连续性审校 / 扫描深度分析 / 素材 JSON / 画布 ops 布局指令 | **0.2** | 输出是判定与结构，要稳 |
| 对话 | 工作室 ask/agent 聊天 | **0.5** | 兼顾事实复述与表达自然 |

**实现三选一（拍板点 P-4）**：

| 方案 | 内容 | 代价 |
|---|---|---|
| A 不做 | 用户手动多建助手（不同温度）自助分档 | 零代码；体验差（用户不懂该建几个） |
| **B 代码侧任务档（推荐）** | `runAgentTextTask`/画布/审校路径按上表传 per-run `temperature` 覆盖 → Rust `run_agent` 增可选参（与 P-1=S 同一批 Rust 手术，签名只动一次）；工作室对话不覆盖（沿用助手值） | Rust 签名+调用点+锁测 1-2 例（照批次 2 先例）；前端一张 `TASK_TEMPERATURE` 映射 + 测试；`cargo test --lib` |
| C UI 配置化 | AI 页表单加「任务温度档位」 | 新设置域 7 件套 + UI 概念负担（写作软件用户被要求理解温度分档），不推荐 |

诚实代价提示：B 落地后**判别类任务的既有回答风格会变**（更收敛、更少发挥），属于「影响全部对话体感」一类，与批次 6 本体同级风险——故必须拍板才动。
