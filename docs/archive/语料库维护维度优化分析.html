二现状核实（维护相关能力盘点）

2.1 存储架构：独立 corpus.db，防崩降级

已确认事实：

  • 语料库独立于业务库：corpus.db 与 config.db 完全隔离（索引体积不拖累主库备份/清理）；PRAGMA 为 WAL + synchronous=NORMAL + busy_timeout=5000 + cache_size=-8000。
  • FTS5 采用 external content 挂 corpus_chunks，配 3 个触发器（INSERT/DELETE/UPDATE）自动同步倒排；tokenizer 为 trigram——中英双语子串检索无需分词器，2 字查询可命中。
  • 建表铁律「只 CREATE TABLE IF NOT EXISTS」：升级一律走 ALTER ADD COLUMN（source_path / content_hash / simhash / norm_hash / category 均为后加列）；依赖后加列的索引（如 idx_corpus_chunks_norm）严格排在 ALTER 批次之后，规避了历史 panic 级踩坑。
  • 可用性降级（B2）：CorpusState 提供 ready / unavailable 两态，corpus.db 初始化失败不再 abort 应用，前端经 corpus_status 探针显示「语料库不可用」横幅并禁用入口。

证据：corpus_database.rs（建表/PRAGMA/ALTER 铁律）、commands/corpus.rs L40-96（CorpusState/status）、lib.rs（命令注册与降级注入）、LibraryPage.tsx L128-158（探针+首刷）。

2.2 导入管线：六格式 + 三层文本净化

已确认事实：

  • 格式分流：txt（UTF-8 优先、GBK 回退）/ epub（container → OPF spine 阅读顺序）/ docx（w:t 按 w:p 分段）/ fb2（跳过 description/binary/style） / html（零依赖容错剥离 + 块级标签补换行 + 实体反转义）/ mobi-azw3（mobi crate，DRM 明确拒绝）。
  • 切分参数：单句上限 400 字符（超长从软标点回退硬切，窗口 120）、短句合并下限 8 字符、语种感知的软换行拼接（英文补空格、中文直连）。
  • 三层净化：格式/站点噪声过滤（纯标点/拟声/求票/水印 → 不入库）→ 短语气应答行例外保留（「嗯。」「啊？」作新段起点并入后续句）→ 参考价值分层（reference.rs：对话/叙事动词/意象/修辞 → High；有效字符 ≥4 → Medium；碎片 → Low 不入库）。
  • 导入即归档：import_book 在单事务内写入书行 + 抽取后全文镜像（corpus_book_sources）+ 全部句子，并一次性算出 content_hash / simhash / word_count / chunk_count。

证据：commands/corpus.rs（extract_text_by_path 及六个抽取器）、pipeline.rs L22-129（常量与净化）与 L241-449（parse_text/切句）、repository.rs import_book。

2.3 索引重建：三级回退，失败不清空

已确认事实：

  • 重建优先级：① 库内全文镜像重切分（源文件移动/删除仍可重建，消除孤儿书）→ ② 无镜像则重读外部源文件抽取 → ③ 都不可用则记为 skipped，不清空既有索引。
  • 重建后事务内整体替换 chunks、刷新统计/指纹，并以新抽取文本 upsert 刷新镜像。rebuild_corpus_index 支持全量或单本（book_id）。
  • 失败分类细粒度：rebuilt / skipped / failed 逐本返回到 RebuildReport（含每本原因）。

证据：commands/corpus.rs rebuild_one 三级回退与 resegment_and_replace、repository.rs replace_book_chunks；单测覆盖「镜像兜底」与「跳过/失败分类」两个场景。

2.4 查重体系：导入前提示 + 全库扫描

已确认事实：

  • 导入前查重：文件指纹与库内比对，命中分级 exact_path（同一文件）> exact_content（去空白全文一致）> similar（SimHash 近似，带相似度%）> same_meta（同名同作者）；只提示不阻断，文件不可读时自动降级为弱信号比对。
  • 全库查重（维护用）：书本级精确组（content_hash / source_path）+ SimHash 近邻贪心聚类（组内取最低相似度，精确组内书不重复列出）+ 重复语句 Top50（norm_hash 分组、跨书聚合、噪声行整组过滤、MAX_GROUP_SCAN=20000 触顶时总数记为下界）。
  • 检索合并：句中重复（同 norm_hash）在检索时非破坏合并（库里不删行），只出代表条 + 出现位置列表（上限 20）+ 范围内次数统计。

证据：commands/corpus.rs duplicate_hits / scan_book_duplicates、repository.rs sentence_dup_groups / merge_duplicate_hits、fingerprint.rs（SIMHASH_NEAR_DUP_MAX_DISTANCE=16）。

2.5 标签体系（P0-3）：已完整落地

已确认事实：此前记忆中的「子线二 P0-3 标签体系升级」经本轮源码核查已在代码层完整落地：

  • corpus_book_tags 表（一对多，PK(book_id, tag)，tag 列有索引）已在建表批次中创建；corpus_books.category 列保留为「顿号连接」镜像并双写同步。
  • 写路径：set_corpus_book_tags（先清后插、trim 去空去重）+ update_book_meta 对 category 的切分双写（逗号/顿号/分号/斜杠均可作为分隔符）。
  • 读路径：标签表优先，表空且 category 非空时回退为单值（兼容 P0-3 前旧数据）；list/search 批量装配一次查询避免 N+1。
  • 检索：search_corpus_books_by_tag（EXISTS 精确匹配）；search_books 的 LIKE 仍覆盖 category 镜像列，旧检索语义不丢。
  • 前端：编辑对话框标签输入、书架顶部标签筛选栏（全量聚合去重）、书卡标签展示；删除书级联清标签行。

证据：corpus_database.rs 建表、repository.rs sync_tags_inner / set_book_tags / attach_tags_one / load_tags_map、commands/corpus.rs 两个标签命令、LibraryPage.tsx 标签交互（L487-505）。

2.6 检索：双通道 + 防呆

已确认事实：≥3 字符走 FTS5 MATCH（trigram 短语 + BM25 排序），<3 字符自动降级 LIKE（ESCAPE 转义 % _ \）；书命中（书名/作者/分类 LIKE）置顶、上限 10；搜索防抖 300ms；重复句合并按检索范围统计（按书过滤时不跨书合并）。

证据：repository.rs search 双通道、commands/corpus.rs search_corpus、LibraryPage.tsx 检索 effect。

三维护维度已知风险与缺口

基于源码核查，语料库核心链路（导入/重建/查重/删除）的正确性防护已较完备（事务包裹、失败不清索引、删除级联、镜像兜底、降级不崩）。以下为维护/规模维度仍存在的真实缺口，按影响面分级。

缺口 A · corpus.db 体积只增不减，无回收手段 P1

  • 现状：镜像表保存每本书的完整抽取全文（正文字数 ×2 层冗余）；trigram 对中文为 3-gram 子串索引，索引体积可观；删除书只删行不回收页；全程无 VACUUM / wal_checkpoint 调用，无任何压缩维护命令。
  • 影响：长期导入 + 反复重建 + 多次删除后，corpus.db 持续膨胀无法回收；对磁盘受限用户是实打实的维护痛点。

缺口 B · 超大文件导入无防护，未知格式静默当 txt P1

  • 现状：import_blocking 用 std::fs::read 一次性整读文件（内存峰值可超文件 2 倍：读取 + 镜像），epub/docx 亦整读入内存；扩展名不在白名单时落入 txt 分支，二进制内容经 GBK 尝试失败后 from_utf8_lossy 以 U+FFFD 乱码进库。
  • 影响：超大文本导入内存/索引时间失控；误选 PDF 等格式会污染语料检索质量，且用户难以定位乱码来源。

缺口 C · 全量重建无进度反馈、无逐本明细展示、前端无单本入口 P1

  • 现状：重建一次性串行跑完（后端已有 per-book 明细与原因，但前端只用 rebuilt/skipped/failed 三个计数 toast 汇总）；后端支持 book_id 单本重建，前端只有全量入口——换源文件更新内容只能「删除 → 重新导入」。
  • 影响：书多句多时重建无可见进度；失败/跳过原因不可见，用户无法定位「为什么这本没重建」；单本重建路径缺失降低了维护摩擦。

缺口 D · 维护操作无并发互斥 P1

  • 现状：import / rebuild / delete / check_duplicate 均在阻塞线程池执行、共享同一 SQLite 连接（Mutex 串行化保证不损坏），但业务层无 in-flight 互斥；前端 importing / rebuilding 标志相互独立，可同时触发导入 + 重建。
  • 影响：重建快照 list_books 先于并发导入取书，混跑时序下新书不在重建目标内；重复点击造成重复执行排队；弱一致性场景无提示。

缺口 E · 导入前查重对选定文件重复全量抽取 P2

  • 现状：check_corpus_duplicate 每次读文件 + 抽取 + 算指纹；前端在 draftPath 变化后 300ms 即触发一次，用户改动书名/作者不会重算（有 ref 优化），但每换一次大文件就要整文件抽取一遍。
  • 影响：超大文件下选文件后有明显等待；换文件反复触发时浪费 IO/CPU。

缺口 F · 标签维护能力边界（无重命名/合并/统计） P2

  • 现状：P0-3 提供设标签与按标签筛选，但无标签重命名/合并/删除、无每个标签的书目计数；前端 allTags 无限增长无折叠。
  • 影响：「仙侠」与「仙侠类」这类近义标签只能逐书手工重设；标签多了之后筛选栏失控。

缺口 G · 检索书命中硬编码顺序扫（规模性退化） P2

  • 现状：书名/作者/分类检索为 LIKE 全表顺序扫 + 上限 10，代码注释明确依赖「书量级小」。句子检索另有 64 位 norm_hash 碰撞与 FTS trigram 的极端低频词场景，属可接受近似。
  • 影响：书量上百小时后书名检索退化明显；当前几十本量级无感。

缺口 H · 语料库存储/维护规约未纳入设计文档 P2

  • 现状：docs/corpus-design.md 覆盖的是「前端 AI 上下文语料」的生产规约（四层模型/五步流程/预算/铁律），未覆盖语料库存储层（本报告 2.1-2.6 涉及）的建表/重建/查重/标签/体积维护约定。
  • 影响：新增语料库能力时缺少「唯一约定」可查，容易再出现实现与文档漂移。

四可落地优化点与优先级

按「影响/成本」排序：P1 为维护体感与规模风险优先处理项，P2 为按需完善项。每项均给出当前代码证据与最小改动路径。

P1-1 提供数据库空间回收命令（VACUUM + checkpoint） 工作量：低

新增维护命令（如 vacuum_corpus_db）：PRAGMA wal_checkpoint(TRUNCATE) + VACUUM，前端在语料库页加「压缩数据库」入口并展示当前库体积；删除书后提示可回收。落点：CorpusDatabase 增加方法 + commands/corpus.rs 注册 + LibraryPage 维护区。成功后 schema 不变、铁律不破。

P1-2 导入防护：文件大小上限 + 未知格式显式拒绝 工作量：低

〈缺口 B〉：导入前校验文件大小（如上限 200MB，超限返回明确 Validation 错误）；扩展名不在白名单时拒绝并提示支持格式，不再静默落 txt；对 GBK/UTF-8 均解码失败或 U+FFFD 占比过高时判定「不可解码」放弃导入，防乱码污染。落点：import_blocking / extract_text_by_path。

P1-3 重建体验：进度事件 + 逐本明细 + 单本重建入口 工作量：中

〈缺口 C〉：rebuild_blocking 逐本完成时经 Tauri event（或分批通道）回传进度与单本状态，前端出进度条与 per-book 结果矩阵（已实现字段 items 直接可用）；书卡操作菜单加「重建索引」（后端已支持 book_id）。

P1-4 维护操作 in-flight 互斥 工作量：低-中

〈缺口 D〉：CorpusState 增加 in-flight 原子标志（import/rebuild/delete 互斥，或统一串行队列），冲突时返回明确错误；前端按钮按该状态禁用，杜绝「重建中又导入」的弱一致与重复排队。注意与既有 Mutex 线程模型的结合位置：互斥放在命令入口而非 SQLite 层。

P2-1 查重指纹缓存（path + size + mtime） 工作量：低

〈缺口 E〉：以 (source_path, 文件大小, mtime) 为键缓存最近一次抽取的指纹，命中直接走比对，避免换文件/重复选择时全量重抽；mtime 变化自动失效。

P2-2 标签维护：重命名/合并/删除 + 计数 工作量：中

〈缺口 F〉：新增标签管理命令（rename：事务内更新 corpus_book_tags 并同步 category 镜像；merge：重复标签归并与去重；delete：解除所有书该标签）；前端标签筛选栏显示各标签书目计数、超限折叠「更多」。

P2-3 书检索退化防护与口径说明 工作量：低

〈缺口 G〉：保留当前实现的前提下，在 docs/corpus-design.md 增加「语料库存储与维护」章节，固化建表铁律、重建三级回退、标签双写、查重口径、规模适用边界（书量级建议 <200 本），并把「书命中上限 10 + LIKE 顺序扫」标注为已知边界；书量增长预警可后续加 64 位前缀索引或 FTS 书名列。

P2-4 文档补齐 + 端到端维护冒烟测试 工作量：低-中

〈缺口 H〉：P2-3 的文档章节即为补口；另可加一条 Rust 集成冒烟测试（真实临时文件：「导入 → 单本重建 → 全库扫描查重 → 删除」全链路 in-memory 断言），覆盖维护操作组合回归，防止后续改动破坏回退链。

五优先级矩阵与建议路线

优先级 项 解决缺口 成本 收益
P1 空间回收命令 A 库膨胀 低 高（长期维护刚需）
P1 导入防护（大小/格式/解码） B 大文件与乱码 低 高（防污染+防失控）
P1 重建进度/明细/单本入口 C 重建体验 中 中高（维护摩擦下降）
P1 维护操作互斥 D 并发弱一致 低-中 中（正确性边界收口）
P2 查重指纹缓存 E 重复抽取 低 中（大文件体感）
P2 标签维护与计数 F 标签治理 中 中（P0-3 功能闭环）
P2 边界文档 + 冒烟测试 G/H 规模边界与文档 低-中 中（防漂移/防退化）

建议路线：P1-1 与 P1-2 可先行（改动面小、风险低、收益直接）；P1-3 与 P1-4 一并排期（都动命令层与前端维护区，可同批实现与回归）；P2 各项按下一轮需求按需并入。全部改动须守住既有铁律：只 CREATE 建表、ALTER 升级、81 个 Rust 单测 + 前端 vitest 全绿后再交付。
