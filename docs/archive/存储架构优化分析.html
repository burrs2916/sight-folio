三磁盘实测三大关键发现

这三条都是本轮打开真实数据库后才确认的事实，其中第一条对上一轮《维护维度分析》的部分结论构成修正。

发现一 · 磁盘上的 corpus.db 还是「旧 schema」：镜像表与标签表根本不存在 修正上轮结论

  • 实测：真实 corpus.db 的 business schema 只有 corpus_books / corpus_chunks / corpus_fts 及两个索引；没有 corpus_book_sources（镜像表）、也没有 corpus_book_tags（标签表），且 corpus_books 表没有 tags 语义列之外的镜像相关列（source_path / content_hash / simhash / category 等后加列已存在，说明经历了部分 ALTER 升级）。
  • 而当前工作区源码 corpus_database.rs（L72-85）明确含这两张表的 CREATE TABLE IF NOT EXISTS——说明含镜像/标签建表的最新代码从未在这份磁盘库上真正运行过。git 状态佐证：corpus 域 7 个 Rust 文件全部处于未提交（M/??）状态，最近一次提交（09-23）早于这些改动。
  • 影响：上轮报告「P0-3 标签体系已完整落地」应修正为——代码层已就绪（含 legacy 升级回归测试），但运行时/磁盘层尚未落地；用户实际运行的是旧二进制或未重编译的开发构建。真实库升级路径（老库补表补列）只被内存库单测覆盖，从未在真实大库上验证。

证据：sqlite3 直查 sqlite_master / PRAGMA table_info；corpus_database.rs L49-101（建表）、L105-126（ALTER 迁移）；git status（corpus 域 7 文件未提交）。

发现二 · corpus.db 61MB 里业务数据 0 行，FTS 残留 50MB——「删除不回收空间」已被实锤 验证上轮 P1-1

  • 实测：corpus_books = 0 行、corpus_chunks = 0 行、corpus_fts = 0 行；但 dbstat 显示 corpus_fts_data 占用 50.1MB、corpus_fts_idx 264KB、freelist（空闲页）2108 页 ≈ 8.6MB，合计数据页 51.3MB。
  • 成因：该库历史上导入过大量书籍并生成了巨型 trigram 倒排索引，之后书籍被删除；而 FTS5 的 external content 删除通过 INSERT INTO corpus_fts(corpus_fts,rowid,content) VALUES('delete',...) 只是标记删除，不会回收段空间；SQLite 删除行也只标记空闲页不归还文件。于是出现「文件 61MB、业务数据 0 行」的空洞库。
  • 影响：上轮 P1-1「库体积只增不减」不是理论风险，而是已经发生的现状；当前这个库可通过 VACUUM + FTS rebuild 直接回收约 50MB（约 82%）。这也是「语料镜像外置」讨论的参照系——真正的体积大头是 FTS 倒排残留，而不是镜像正文。

证据：sqlite3 SELECT COUNT(*) 三表全 0；dbstat 按对象聚合；PRAGMA freelist_count=2108 / page_count=14945 / page_size=4096。

发现三 · config.db 当前近乎空壳，写作域为发育早期 澄清规模认知

  • 实测：写作域仅 1 本书（「新建作品 1」）、7 章、正文合计 7 字符，章节快照 0 条，daily_stats 15 条；全库最大的表 analyses 也仅 28KB；其余 AI/代码分析/设置表大多 4KB（空表）。
  • 影响：当前 config.db 2.4MB 无法代表真实规模；「写作正文存 TEXT 列」的膨胀风险尚未被数据量压测。做增长预估时必须按「每本书 × 章节数 × 平均章字数 + 每日快照」建模，而不是拿现在 7 字符推算。

证据：writing_books=1、writing_chapters=7 且 SUM(LENGTH(content))=7；dbstat 全表页数。

四三条优化观察线的取舍分析

4.1 观察线 A · 语料镜像是否应外置为文件？ 结论：保持入库，不做外置

  • 现状：源码设计将全文镜像存 corpus_book_sources.raw_text（入库），重建时三级回退「①库内镜像 → ②外部源文件 → ③skip」依赖它兜底（源文件丢失后仍可重建）。磁盘实测该表尚未真正建出（见发现一），属「待落地」状态。
  • 外置的好处：正文少存一份（chunks.content + 镜像双份 → 只存文件），语料库文件更小。
  • 外置的代价（更重）：① 破坏三级回退的第一级兜底——源文件被移动/删除后无法重建，这正是镜像设计的核心价值；② 备份从「单文件 corpus.db」变成「库 + 目录」两处，易漏；③ 路径搬迁、跨设备同步都要处理相对路径。
  • 取舍结论：真正的体积大头（实测 50MB）是 FTS 倒排索引残留，不是镜像正文；镜像入库对重建可靠性的收益远大于那点体积成本。推荐保持镜像入库，把精力放在「回收 FTS 空间」上（见 4.2）。

4.2 观察线 B · config / corpus 双库增长预估与回收手段 结论：需要回收命令 + 分库容量认知

增长模型（按源码字段与表设计推导）：

  • config.db：写作正文（content TEXT）× 章节数 + 每章快照 + daily_stats 按天累积 + 代码分析四算表。当前空壳不可作参照；按单书 60 万字、20 章、每章 3 万字估算，正文列首个文本数量级约数 MB，快照若每次保存全章会成倍放大——快照策略是 config.db 增长的隐藏变量。
  • corpus.db：正文（chunks.content）+ 镜像（raw_text，双份）+ FTS trigram 倒排。trigram 对中文 3-gram 子串的倒排膨胀系数高，实测曾经的书量级即留下 50MB FTS。增长大头是 FTS 而非正文。
  • 回收能力（当前缺失）：库内无任何 checkpoint / VACUUM / FTS rebuild 命令；删除书、重建索引都只标记不回收。上轮 P1-1 建议的「压缩数据库」命令即为本题答案，且应包含 FTS rebuild（单纯 VACUUM 不压缩 FTS 残留段，必须 INSERT INTO corpus_fts(corpus_fts) VALUES('rebuild') 重写倒排）。

推荐（并入上轮 P1-1 一并实现）：

  1. 新增维护命令：wal_checkpoint(TRUNCATE) + FTS rebuild + VACUUM；前端「语料库」页展示库体积与可回收空间。
  2. 导入/重建后自动轻量回收或在删除书后提示「空间待回收」（避免每次导入都全量 VACUUM 的性能代价）。
  3. config.db 快照策略纳入容量预估：确认章节快照是否全量存正文，若是，考虑增量/阈值化。

4.3 观察线 C · localStorage 设置是否归并入库？ 结论：分级处理，不整体归并

层级 现有存储 取舍 推荐
UI 偏好（主题 / 语言 / 排版 / 布局） localStorage 高频写、低价值、换机重建成本低；入库需走 IPC 且换设备还要另做同步才有意义 维持 localStorage，仅统一键 schema 版本与清理钩子（在 cacheWhitelist 基础上补齐）
AI 配置与创作预设（ACP host / Agent presets） localStorage 属「创作资产」，随库备份可迁移、可版本化；localStorage 无法进入 config.db 备份体系 建议迁入 config.db（ai_* 表或 user_settings JSON），本地仍缓存一份做首屏加速
认证态（token 族） localStorage 明文写 SQLite 有安全顾虑（桌面应用更应走系统凭据库）；现状已能支撑登录态 绝不入 SQLite；长期可评估迁移到 macOS Keychain / 系统凭据 API

这里需要用户决策的子问题只有一个：「Agent 预设」等 AI 创作配置是否入库——它将决定后续做「设置统一备份/迁移」时的范围。其余两级维持现状即可。
