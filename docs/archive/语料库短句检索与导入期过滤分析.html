语料库短句检索与导入期过滤分析

现状核实：单字/两字句子为什么能进索引 · 实施前方案：导入书籍时按最小有效字符门槛过滤

📅 2026-09-27 📁 范围：导入管线（pipeline / reference）＋ 检索链路（FTS / LIKE） 🔒 性质：只读分析，不含代码改动

01结论摘要

现象成立：搜索 1–2 字词语时，结果会混入「单个文字的句子」与「两个字组成的句子」（如 “好。”、走吧。、嗯。）。根因不在搜索端，而在导入期：现有过滤只判 「内容样式（噪声）」和「叙事信号（参考价值）」，没有最小索引长度门槛。凡携带对话、叙事动词或意象 信号的 1–2 字短句，导入时被当作 High 参考价值保留。

短句入库的三个出口（详见第 02 节）：

  • 出口A带引号的单字对话：“好。” 含对话引号对 → tier_of 判 High → 入库；
  • 出口B含叙事动词 / 意象词的 1–2 字短语：走吧。（“走”∈叙事动词）、风大。（“风”∈意象词）→ High → 入库；
  • 出口C独立语气行在文件末尾 / 章节标题前落库：嗯。 走 pipeline 的直推分支，tier恒为 High，绕过 tier_of 的长度兜底 → 入库。

搜索命中原因（详见第 03 节）：查询字符 < 3（中文单字/双字词最常见）时检索走 LIKE %q% 直扫 corpus_chunks.content——该路径无长度过滤、无 kind 过滤、无 tier 过滤，库里所有含该子串的短句 chunk 全部命中。

方案一句话：在导入期对「合并后的索引单元」加最小有效字符门槛（推荐 有效字符 < 3 → 不入索引）， 共两处小改（tier_of 顶部加长度规则 ＋ 语气行落库改走 tier_of 判定）。搜索侧、库表结构、FTS 倒排、章节标题索引均不动； 存量书重建一次即清除旧短句（重建指纹比对会自动触发 replace，无需迁移脚本）。

2.2 短句漏网的三个出口

出口 示例（有效字符） 放行依据 tier 结论
A · 引号对话 “好。”（1 字） 含“”引号对 → 对话信号 High → 入库
B · 叙事/意象词 走吧。（2 字）· 风大。（2 字） “走”∈叙事动词、“风”∈意象词 High → 入库
C · 语气行落库旁路 嗯。（1 字，文件末尾/章标题前） pipeline.rs L265 / L292 / L326 直接 push，tier 写死 High High → 入库（绕过 tier_of）

结论：能入库的 ≤ 2 字短句全部携带「设计保留」的信号——不是漏检，而是现行规则 只有样式维度和信号维度、没有长度维度的必然结果。无信号的 1–2 字句（如裸好。）实际已被 tier_of → Low 挡住；用户搜到的短句，是上面三类「带信号」的。

2.4 复现示例

搜「好」（1 字，<3 字符）  → LIKE '%好%'      → 命中库中 High tier 的短句 chunk “好。”
搜「谢谢」（2 字，<3 字符） → LIKE '%谢谢%'    → 命中库中短句 chunk 谢谢。
搜「走吧」（2 字，<3 字符） → LIKE '%走吧%'    → 命中库中 High tier 的短句 chunk 走吧。

触发前提：库里确实存在这些短句 chunk（由 2.2 的三类出口在导入时写入）。本机开发库 data/corpus.db 当前不存在（未运行调试版导入），结论由代码事实与既有单测支撑。

03方案设计：导入期过滤（实施前）

3.1 目标与原则

目标索引中不再出现有效字符 < 3 的句子单元；搜索侧行为、库表结构、FTS 倒排、章节标题索引全部保持现状。
原则① 只挡最终索引单元过滤放在短句合并之后、入库之前——合并优先，完整句（“嗯。”＋他点点头…）不受影响。
原则② 不丢原文仅挡索引单元；抽取全文镜像（source_text）原样保留，重建可完整恢复。
原则③ 不动检索语义< 3 字 LIKE 子串命中的能力保留（搜“好”仍命中“好的很”），只是不再有“好。”这种短句本体出现在结果里。

3.2 推荐规则：有效字符 < 3 → 不入索引

新增常量（reference.rs，与 effective_chars 同处）：

/// 最小索引单元长度（有效字符数）。短于该值的句子（1–2 字碎片）无索引价值，导入即不入库。
const MIN_INDEX_CHARS: usize = 3;

规则 ①：tier_of 最前加一条：effective_chars < MIN_INDEX_CHARS → Low（不进入索引）， 无论是否含对话/叙事/意象/修辞信号。此时 Low 的语义从「无信号且信息量不足」扩展为「无信号且不足，或长度不足」——长度是充分条件。

规则 ②：pipeline.rs 三处语气行落库（L265 / L292 / L326）的 tier 由「恒 High」改为 tier_of(&tone) 判定——独立语气行落库时同样经过长度门槛；若该语气行已并入后续正文句（合并单元有效字符充足），照常保留。

3.3 效果对照

输入样例 有效字符 现行 改后 说明
“好。”（孤立对话） 1 入库 不入库 单字对话不再单独成索引单元
“好。”你终于来了。（并入后句） 6 入库 入库 合并单元完整，不误伤对话上下文
嗯。（EOF/章标题前落库） 1 入库 不入库 语气行落库旁路被长度规则覆盖

第一章 出山（章节标题） — 入库 入库 kind=chapter 不经 tier_of，始终保留导航结构

3.4 阈值讨论：为什么选 3

  • 对齐用户诉求：要拦的是「单个文字」「两个字组成」的句子——有效字符 < 3 恰好只拦 1–2 字；
  • 不误伤完整短句：他走了。（3 字）是常见且值得参考的完整句，保留；
  • 英文等价：OK.（2 字）拦、Yes.（3 字）留，口径一致；
  • 与现有门槛并存：tier_of 已有「无信号且有效字符 < 4 → Low」，新增长度门槛只收紧「带信号短句」，两者互补不冲突；
  • 备选 4 若嫌 3 字句（如他走了。）也碎，阈值可提至 4——同一常量一处改动即生效，无需另设计。

3.5 插入点与改动面（最小改动）

改动 位置 改什么
① 长度规则 domain/corpus/reference.rs tier_of 顶部加 `effective_chars < MIN_INDEX_CHARS → Low`；新增常量 1 个
② 语气行落库判级 domain/corpus/pipeline.rs L265/L292/L326 3 处 `tier: High` → `tier: tier_of(&tone)`
不改 其余全部 is_noise_text / 短句合并 / flush_paragraph
import_book・SQL・FTS 表・搜索查询		 保持不变——过滤只发生在切分管线出口，索引形态之外零接触

对比插入点方案（不推荐）：在 push_sentence 直接丢弃短句会破坏「短句在线合并」机制 （“好。”被删后你终于来了。失去引号上下文）；在 SQL 入库层过滤会绕过 tier 语义且不利于测试。 统一放在 tier_of（合并之后）是语义与最小改动的交点。

3.6 存量书如何生效：重建即清除，无需迁移

重建链路 rebuild_one 的机制是「镜像重切分 → book_fingerprints 与库内比对 → 不一致则 resegment_and_replace 替换」。parse_text 输出少了短句 → 该书的指纹集合变化 → 自动触发 replace， 短句 chunk 连同 FTS 倒排一并清除。

因此实施后的存量清理动作就是：对既有书目跑一次重建索引（现有功能入口即可，全量跑一次全库生效）。 注意 不做重建则已入库短句仍留在库里——这是「导入期方案」语义上的必然后续，实施时应顺带引导用户重建。
