## 2. 🔴 P0 新发现：「重启失效」的结构性成因在**库落点**，不在前端链路

### 2.1 四条实测证据

**证据 A —— 设置库里只有 3 个键，且全是旧 payload 形态。**
`data/config.db` → `user_settings` 表全文（只读连接 `mode=ro` 取的，含 WAL）：

```
key                  updated_at(epoch)   value
theme                1793595717          {"mode":"light","preset":"purple","fontSize":"medium","borderRadius":"round"}
layout               1793595717          {"preset":"default","sidebarCollapsed":false,"sidebarWidth":240,
                                         "sidebarPosition":"left","contentPadding":"large","navbarStyle":"standard"}
appearance_profiles  1793595717          {"version":2,"profiles":[],"activeProfileId":"violet",
                                         "baseProfileId":"violet","isModified":false}
```

`1793595717` = **2026-11-02 13:01:57**，三行同一秒 ⇒ 像是一次批量写（备份恢复的特征），不是逐次用户调节。
对照当前代码，这三行的字段形态**全部落后两到三个版本**：

| 键 | 库里的形态 | 当前代码写入的形态 | 差什么 |
|---|---|---|---|
| `theme` | 4 字段 | 7 字段（`themeStore.ThemeConfig`） | 缺 `motion`（21 轮）、`uiFont`（26 轮） |
| `layout` | 6 字段 | 8 字段（`layoutStore.LayoutConfig`） | 缺 `contentWidth`（21 轮）、`fullBleedFollowsLayout`（27 轮，就在刚才落的） |
| `appearance_profiles` | `version:2` | `_persist()` 恒写 **`version:3`**（`appearanceStore.ts:375`） | 说明这条读数**不是当前构建写的** |

**证据 B —— 当前构建「一定会写」的 4 个键，库里一个都没有。**
- `language`：`languageStore.init()` 在「库里没读数」时会把 i18n 推导值**无条件落库**
  （`languageStore.ts:83-86`，注释自己写着「全新安装：把推导读数落进设置库」）。跑过一次就会有这行。
- `writing_typography` / `writing_prefs`：第 24~26 轮建的两域，改档即写。
- `settings_probe`：`settingsHealthStore` 每次启动写的健康探针（`settingsHealthStore.ts:138`）。

四个键同时缺席 + 三个存在的键都是旧形态 ⇒ **`data/config.db` 从 13:01:57 之后就没再收到过当前构建的写入。**

**证据 C —— 生产包的库落在「可执行文件同级目录」，路径每变一次就是一个新世界。**
`src-tauri/src/infrastructure/database/connection.rs:144-160`：

```rust
pub fn app_data_dir() -> PathBuf {
    let dir = if cfg!(debug_assertions) {
        /* dev  */ project_root.join("data")
    } else {
        /* prod */ std::env::current_exe()?.parent() /* = Sight Folio.app/Contents/MacOS/ */
    };
    ...
}
```

生产候选链（`candidate_paths`，同文件 97-107）是 ①`exe 同级/config.db` → ②`app_handle.path().app_data_dir()/config.db`
→ ③内存库。**关键在于第 ② 档只在第 ① 档 open 失败时才会被用到**，而 `.app` 放在桌面 / 下载 / 构建输出目录时
`Contents/MacOS/` 通常是**可写的** —— open 成功，于是库就静静地待在 app 包里，于是：

- 重新 `tauri build` 换产物、把 `.app` 从 `target/release/bundle/macos/` 拖到 `/Applications`、
  从 DMG 直接双击、换一台机器 —— **每一种都是另一个空库**，界面一路显示「已自动保存」，关掉全蒸发；
- 这正是第 23 轮文件头注释自己写的病灶（"生产包里 config.db 落在可执行文件同级目录…每次换路径的构建产物启动时"），
  第 23 轮补的是「open 失败别静默退内存库」，**没有补「成功但落点不稳定」这一支**。

**证据 D —— 退路从未被启用过，说明第 ① 档一直在"成功"。**
`tauri.conf.json:5` 的 identifier 是 `com.sight.folio`，而
`~/Library/Application Support/com.sight.folio` **不存在**（实测 `No such file or directory`）；
Application Support 下只有一个空的 `com.project-sight/icons/`（7 月 30 日留下的旧 identifier 遗迹，里面没有 db）。
⇒ 系统用户数据目录这条路从来没走过。开发库（`./data`）从 13:02 起没被写过，生产库位置则跟着 `.app` 走。
**两边对不上，就是「我明明设过，重启就没了」。**

（附：本机 `src-tauri/target/` 存在但没有 `bundle/macos/`，说明当前工作区没打过生产包 ——
李先生手上跑的那个 `.app` 不在这个仓库里，它的库也就不在这里。这条与 §2.1 结论一致，不是矛盾。）

### 2.2 修法建议（给下一轮，一刀三处，按顺序做）

1. **落点口径反转**：生产主路径改成 Tauri 的 `app_data_dir()`（macOS = `~/Library/Application Support/com.sight.folio/config.db`），
   把「exe 同级」降级为**兼容老库的迁移读**（检测到 exe 同级有 db 且用户数据目录没有 → 复制过去一次，
   并在日志/界面说明"设置库已迁到稳定位置"）。`Database::new` 的候选链重排即可，PRAGMA 那套不动。
2. **界面说实话的口径补全**：`database_status()` 目前只回 `(persistent, location)`。
   建议 location 之外再带上 `generation`（同一 db 的 inode/大小指纹即可），让 `SettingsHealthNotice`
   能在「这次启动的库和上次不是同一个」时直接说一句人话，而不是只显示路径让用户自己比对。
3. **测试锁**：Rust 侧对 `candidate_paths()` 的纯函数断言（dev/prod 顺序、alt 与 primary 相同时不重复）；
   前端对 `SettingsHealthNotice` 补一条「dbLocation 变了要显示出来」的锁。
   注意本仓铁律：**门禁读数必须是实测值**，Rust 测试跑不动就先写清「未跑」。

## 4. 🔴 P1 新发现：书级排版覆盖存在 **localStorage**，不在设置库、不在备份、不在跨窗口广播

`src/utils/typography.ts:145 / 169-205`：优先级写着「**书级覆盖（localStorage）** > 全局默认（设置库）」，
`saveTypography()` 直接 `localStorage.setItem(keyOf(bookId), …)`，`catch` 里静默忽略。

后果（与前几轮已修的病灶同型，只是藏在书级这一支）：
1. 用户在写作台给某本书单独调的字号/行距/纸色 **不进 `user_settings`**；
2. `BACKUPABLE_SETTINGS_KEYS`（`utils/settingsBackup.ts:47-54`）只有 6 键，**书级排版不在导出里** ——
   「导出备份」看着完整，换设备导回来每本书的排版全回全局默认；
3. 不在 `settingsSyncStore` 的 6 个 scope 里 → **没有失败重试、没有状态读数**，写失败连 toast 都不会有；
4. 不在 `appearance-changed` 广播里 → **写作台独立窗口不跟随书级排版**；
5. WKWebView 的 localStorage 随 `.app` 路径变化 / 清缓存即丢 —— 与 §2 的落点问题叠加时，
   现象正是「设置没记住」。

**建议口径**（这是「设置功能不完整」当前最实的一块，也是天然的扩展位）：
把书级覆盖从 localStorage 迁到设置库 KV（键如 `writing_typography_book:<bookId>` 或一个
`bookTypographyOverrides` map），走 `persistSettings` 可信层 + 备份键表 + 跨窗口广播，
localStorage 读数保留一个「读到时迁一次并清掉」的老库兼容分支（`languageStore.ts:69-81` 的 legacy 分支就是现成模板）。
**改动面**：`utils/typography.ts`（同步读点不能等 IPC → 沿用「store 单向推入模块级读数」那套口径）、
`typographyDefaultsStore` 加 book 维度、备份 6→7 键、`App.tsx` hydrate 分发、抽屉/写作台面板的显示口径同步。
**别**顺手把它做成「自动」—— 书级覆盖的存在理由就是每本书不一样。
