## 3. 根因

`src/services/core.ts:9-21` 的守卫对每个命令直接 reject（设计如此，为了不把 `undefined.invoke` 的 TypeError 打进控制台）。
而 `src/services/settings.ts` **只有 invoke 这一条通道**，于是浏览器里：七域 init 全部读不回 → 健康条判 `unavailable` → 用户怎么改都是空的。
这是**环境本来没有后端**，不是库坏；但界面给的读数长得跟"库坏了"一模一样。

## 4. 落地（`src/services/settings.ts` 整文件重写，对外 API 形状不变）

双通道，判据只有一个 —— 进程里有没有 IPC 桥：

- **桌面壳内**：四个方法各自 `if (inTauriShell()) return invoke(...)`，**失败原样 reject**，桌面分支外面没有 `try` 包住。
  这条是刻意的红线：一旦给桌面分支也加浏览器兜底，一个已经丢掉整套设置的进程会对着健康条说"没问题"，
  等于把第 23 轮立 `get_database_status`（`connection` 打不开磁盘库时静默退内存、界面照说已保存）要消灭的那类谎重新引进来。
- **纯浏览器**：走 localStorage，键挂 `sightfolio.settings:` 前缀；`databaseStatus()` 自报
  `{ persistent: true, location: '(browser localStorage)' }` —— 健康条那行「设置库存放位置」因此**不说谎、不冒充 config.db**。
- **两边都不可用**（隐私模式 / 存储被禁）：reject，让健康条继续说实话，不静默成功。

已知边界（写进文件头注释，不是漏网）：浏览器兜底**不进备份导出**、**不跨窗口广播**（广播走 Tauri 事件，见 `settingsSyncStore`）。
