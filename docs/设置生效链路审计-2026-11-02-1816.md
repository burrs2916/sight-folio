## 4. 🟡 新发现 B（P2，观察性质，别顺手改）：`hydrate()` 会被读回防护判成「用户改过」

**取证**：`themeStore.ts:349-353`

```ts
hydrate: (config) => {
  const next = normalizeThemeConfig(config);
  if (isSameThemeConfig(next, get().config)) return;
  set({ config: next });          // ← 订阅者看到 config 换了 ⇒ 防护记一次 dirty
},
```

防护订阅的是 `select: (s) => s.config`，**分不出这次换值是「本窗口用户点的」还是「另一个窗口广播来的」**。
后果（只在启动 ≤1.5s 那个窗口里成立，此时本窗口 `init` 还在飞）：

- 迟到库读数回来 → 合并时把广播来的那几项当「内存优先」→ **这个窗口会调一次 `persist(merged)`**
  → 多一次落库 + 多一次广播 + `settingsSyncStore.lastSavedAt` 被刷新
  → 该窗口抽屉底部那句「已自动保存 · HH:MM:SS」**在用户一次没碰过的情况下出现了时间戳**。

**判级与处置建议（重要：不要按「去抖」思路修）**：
- **数据结果是对的**（该保的新值保住了），而且这次写多半还是**必要的**（`merged` 顺手把「内存没初始化就整份落库」
  时被默认值冲掉的其余维度修回去了）；后果只有**那句状态文案的归因不准**，且窗口局限于首帧门控那 1.5s。
- **绝不可以**把 `hydrate` 从 dirty 判定里摘出去 —— 摘了就等于让迟到库读数重新盖掉另一窗口刚广播的新值，
  那是把第 34 轮修好的东西退回去。
- 若将来要收准：做法是给 guard 加一个「本次变更来自外部」的来源标记，**只影响状态上报，不影响合并取舍**。
  优先级低于批次 4，**别和批次混同一刀**。
