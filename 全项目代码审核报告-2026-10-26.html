② 必须先修的高危清单（决定路线的 15 条）

按「安全 → 数据完整性 → 稳定性 → AI 前置条件」排序。这 15 条不修，AI 写工具上线等于裸奔。

安全 · S1 datasource.rs:205-335 — 任意 SQL 直接执行

db_execute_query 接受前端传来的任意 SQL 字符串，无长度限制、无超时、无语句类型白名单，可 DROP 任何表。建议：只读白名单（SELECT/EXPLAIN）+ 超时 + 行数上限；写操作必须走专用参数化命令。

安全 · S2 project_scan.rs:1351-1375 + tools.rs:2816-2837 — 外部命令注入面

git 命令的 -C 参数直接取命令输入未做规范化校验；run_command 黑名单用大小写敏感 contains() 匹配可被绕过。建议：cwd 白名单限定项目根 + 路径规范化；run_command 改为白名单动词或 AST 级解析。

安全 · S3 agent.rs + migration.rs — API Key 明文落库且原样返回前端

ai_providers.api_key 为 TEXT 明文；ProviderDto 将 api_key 直接下发到前端（任何 XSS 或日志都会泄漏）。建议：落库加密（OS keychain 或 AES + 机器绑定），接口只返回掩码。

数据完整性 · D1 writing_repository.rs:1022-1044 + commands/writing.rs:53-80 — 删除链路非事务

delete_storyline 的 DELETE+UPDATE、delete_writing_book 的删除传播均不在同一事务，部分成功会留下孤立引用。AI 写工具上线后批量操作会放大此风险。建议：全部收敛进 conn.transaction()。

稳定性 · T1 mod.rs:27-82 + file_watcher.rs:49-179 — 全局锁裸 unwrap

RUN_CANCEL_TOKENS / TOOL_APPROVALS 静态 OnceLock<Mutex> 每次 lock().unwrap()，中毒即 panic 崩溃整个进程；file_watcher 同模式。建议：map_err 返回明确错误。

稳定性 · T2 agentStore.ts:578-614 — sendMessage 收尾竞态

run 返回后重复 await loadMessages，后一次覆盖 settleStream 的收尾，存在中间窗口重渲染与状态错乱。动作卡片依赖稳定的流式收尾，必须先修。

稳定性 · T3 WritingPage.tsx:942/1464 — 丢稿风险

卸载 flush 为 fire-and-forget，崩溃/强退绕过关窗拦截即丢稿；关窗 await flushSave 无超时。建议：localStorage 快照兜底 + 启动恢复扫描 + 关窗 5s 超时强制销毁。

AI 前置 · A1 engine.rs:278 — 审批闸门只覆盖 run_command

写工具（未来的 save_chapter_draft 等）执行前没有统一审批拦截。必须把 approval 通道泛化为「按工具危险等级」的策略表，这是 AI 接管写操作的唯一安全护栏。

AI 前置 · A2 engine.rs:378-380 + 178-192 — 工具输出与上下文无预算

工具结果原样全量进 messages，长会话上下文无限膨胀。写工具输出（整章正文）远大于只读工具。建议：统一最大长度 + 截断提示 + 历史滑动窗口。

AI 前置 · A3 消息模型无 blocks 字段

AiMessage 仅 content 文本 + tool_calls 字符串，MessageBubble 无结构化块渲染钩子，store 无动作确认回调通道。动作卡片协议需先扩展消息模型与渲染器。

安全 · S4 code_write.rs:92-134 — 写盘防御链失效组合

canonicalize 失败回退原路径（校验形同虚设）、备份失败阻断写入、写盘边界自动建父目录。AI 代码补丁工具路径以此为基础，需逐条收紧。

数据完整性 · D2 migration.rs:1632-1658 — 迁移列清单漂移

writing_chapters 多次 ALTER 复用旧 ch_cols 变量，新旧表结构判断可能漂移。建议每次 ALTER 前重新 PRAGMA。

⑩ AI 优化决策建议（基于审核结论修订）

结论方向不变，顺序修正：先修地基，再上写工具

审核确认了上轮方案的可行性 —— 写工具/动作卡片/计划模式的基础设施大部分已存在（change_ledger 台账、.bak 备份、审批通道、writingStore 标准化 actions）。但也发现 3 类「不修就不能上」的地基问题：审批闸门只覆盖 run_command（写工具会裸奔）、工具输出无预算（写整章会撑爆上下文）、消息模型无块结构（动作卡片没有载体）。因此 P0 从「直接做写工具」调整为「地基加固 → 写工具 MVP」两段式。

阶段 0地基加固（约 15 项修复，先于一切 AI 写能力）

  • 安全：datasource SQL 白名单；git cwd 校验；run_command 黑名单换白名单；api_key 加密落库 + 接口掩码；CSP 收紧
  • 数据完整性：delete_storyline / delete_writing_book 事务化；迁移列清单防漂移
  • 稳定性：全局锁 unwrap 治理；agentStore 收尾竞态；WritingPage 关窗超时 + 快照兜底防丢稿
  • AI 前置：审批闸门泛化（按工具危险等级）；工具输出预算 + 历史滑动窗口；git 工作区分批提交

阶段 1AI 写工具 MVP —— 跑通「写一章 → 审阅 → 一键入稿」闭环

  • save_chapter_draft（改前自动快照）+ update_character_card，复用 change_ledger 台账
  • 两个工具接入泛化后的审批闸门（写入类低危可会话级记住，删除类高危逐条确认）
  • 前端确认卡：writingStore actions 已具备直接调用条件（审核确认签名适配），仅需把 useAiActions 抽出纯函数版
  • 同步补 engine.rs / agent.rs 核心路径测试（审核发现零覆盖）
